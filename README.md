# Fraud Detection System
Fraud Detection System — это веб-система для выявления подозрительных банковских транзакций и управления расследованиями возможного мошенничества. Клиенты банка могут просматривать информацию о своих банковских картах и историю транзакций, а также сообщать о подозрительных операциях. Аналитики безопасности проверяют отмеченные системой транзакции, проводят расследования и фиксируют результаты проверки. Администраторы управляют учётными записями пользователей, назначают роли и настраивают правила обнаружения мошенничества. Система анализирует транзакции по заданным правилам, например выявляет операции с необычно крупными суммами или большое количество платежей за короткий промежуток времени. Система хранит информацию в единой базе данных и позволяет отслеживать статус каждой проверки. Разграничение прав доступа обеспечивает защиту данных клиентов и ограничивает действия пользователей в соответствии с их ролями.
# Сценарии использования системы (Use Cases)

| ID | Роль | Сценарий | Результат |
|---|---|---|---|
| UC1 | Клиент | Просматривает список своих банковских карт | Отображается список карт клиента |
| UC2 | Клиент | Просматривает историю транзакций по своей карте | Отображается список транзакций с датами, суммами и статусами |
| UC3 | Клиент | Сообщает о подозрительной транзакции | Создаётся обращение для проверки аналитиком |
| UC4 | Аналитик безопасности | Просматривает список подозрительных транзакций | Отображается список операций, требующих проверки |
| UC5 | Аналитик безопасности | Проверяет подозрительную транзакцию и фиксирует результат расследования | Сохраняется результат проверки и обновляется статус расследования |
| UC6 | Администратор | Создаёт или изменяет правило обнаружения мошенничества | Новое или изменённое правило сохраняется в системе |
| UC7 | Администратор | Просматривает список пользователей и изменяет их роли | Список пользователей обновляется с учётом изменений прав доступа |

## Обоснование решений

### 1. Почему выбрана трёхуровневая архитектура?

Для Fraud Detection System выбрана трёхуровневая архитектура: уровень представления (Frontend), уровень приложения (Backend) и уровень хранения данных (Database). Такое разделение позволяет отделить пользовательский интерфейс на HTML, CSS и Razor Views от бизнес-логики на C# и хранения данных в MySQL. Если бы браузер работал с базой напрямую, учётные данные для подключения могли бы попасть к пользователю, а проверка прав доступа и бизнес-правил была бы сложнее в централизованном управлении.

### 2. Какие данные хранятся в базе данных, а какие у клиента?

В MySQL хранятся пользователи, банковские карты, транзакции, правила обнаружения мошенничества, подозрительные случаи и результаты расследований. В браузере находятся отображаемые данные страницы и временное состояние интерфейса; аутентификационная cookie может храниться браузером и передаваться серверу с запросами. При этом пароли базы данных и критически важная бизнес-логика не должны находиться на клиенте. Если хранить основные данные только в браузере, их будет трудно надёжно сохранять, согласовывать между пользователями и защищать от подмены.

### 3. Где применяется принцип stateless и как сервер узнаёт пользователя?

В системе используется HTTP, который сам по себе не сохраняет состояние между запросами. При использовании cookie-аутентификации браузер передаёт аутентификационную cookie с последующими запросами, а ASP.NET Core проверяет её и определяет пользователя; сервер может использовать защищённую cookie без хранения пользовательской сессии в памяти приложения. Данные транзакций и расследований сохраняются в MySQL, а не в состоянии отдельного HTTP-запроса. Если бы сведения о пользователе хранились только в памяти одного экземпляра Backend, масштабирование приложения и восстановление после перезапуска были бы сложнее. При этом cookie-аутентификация сама по себе не гарантирует полностью stateless-архитектуру: фактическая реализация зависит от настроек аутентификации и хранения сессий.

### 4. Почему выбран монолит?

Для Fraud Detection System выбран модульный монолит на ASP.NET Core MVC. Все основные модули — Auth, Users, BankCards, Transactions, FraudRules, SuspiciousCases и Investigations — работают в одном приложении, но разделены по назначению и взаимодействуют через внутренние вызовы. Это упрощает разработку, тестирование, развёртывание и выполнение операций с общей базой данных. Если бы каждый модуль был отдельным микросервисом, потребовались бы дополнительные механизмы сетевого взаимодействия, мониторинга и согласования данных. Разделение на микросервисы можно рассмотреть в будущем, если нагрузка на отдельные модули существенно вырастет или возникнет необходимость независимо развёртывать и масштабировать их.

### 5. Какие проверки выполняются на сервере и почему их нельзя оставить только на клиенте?

На сервере проверяются аутентификация пользователя, его роль и права доступа, корректность входных данных и соблюдение бизнес-правил. Например, клиент не должен получать административные права, а обработка подозрительной транзакции должна соответствовать правилам системы. Проверки HTML и JavaScript на клиенте полезны для удобства пользователя, но их можно обойти, отправив запрос напрямую или изменив данные в браузере. Поэтому окончательное решение о доступе и допустимости операции принимает Backend, а ограничения базы данных дополнительно помогают поддерживать целостность данных.

## Риски

В процессе разработки и эксплуатации Fraud Detection System необходимо учитывать риски, связанные с доступностью сервера, защитой пользовательских данных, работой базы данных и корректностью обнаружения подозрительных транзакций.

| Риск | Компонент или связь | Последствие | Как снизить риск |
|---|---|---|---|
| Недоступность базы данных | MySQL ↔ Backend (ADO.NET) | Система не сможет получать сведения о транзакциях, банковских картах и подозрительных случаях. Пользователи не смогут полноценно работать с приложением. | Настроить ограниченное время ожидания подключения и выполнения запросов, обрабатывать ошибки соединения, вести журнал ошибок и регулярно создавать резервные копии базы данных. |
| Подбор пароля или кража учётной записи | Auth, Users, Authorization/RBAC | Злоумышленник может получить доступ к чужим данным или функциям системы, если успешно войдёт под чужой учётной записью. | Хранить пароли только в виде стойких хэшей с солью, использовать HTTPS, ограничивать частоту попыток входа и проверять права доступа при каждом защищённом запросе. |
| Несанкционированный доступ к банковским данным | Authorization/RBAC, Transactions, BankCards | Пользователь может просматривать данные, которые ему не принадлежат, или выполнять действия, не предусмотренные его ролью. | Проверять права на сервере, разграничивать доступ по ролям и проверять принадлежность банковских карт и транзакций пользователю. Не полагаться только на ограничения интерфейса. |
| Перегрузка Backend или базы данных | ASP.NET Core MVC, Service, Data Access, MySQL | Страницы могут загружаться медленно, запросы — завершаться по тайм-ауту, а приложение — становиться недоступным. | Оптимизировать SQL-запросы, создавать индексы для часто используемых полей, устанавливать ограничения времени ожидания и контролировать нагрузку. При необходимости масштабировать приложение и базу данных. |
| Ошибки в правилах обнаружения мошенничества | FraudRules, Transactions, SuspiciousCases | Законные транзакции могут ошибочно помечаться как подозрительные, а мошеннические операции — оставаться незамеченными. | Тестировать правила на подготовленных наборах транзакций, проверять изменения перед публикацией, вести журнал изменений и предусмотреть возможность корректировки правил администратором. |
| Потеря или повреждение данных | MySQL, таблицы Transactions и Investigations | История операций и результаты расследований могут быть потеряны, что затруднит анализ инцидентов и восстановление работы системы. | Регулярно создавать резервные копии, ограничивать права изменения данных, использовать транзакции для связанных операций и периодически проверять возможность восстановления из резервной копии. |

### Приоритетные риски

Наиболее критичными для системы являются несанкционированный доступ к банковским данным, потеря информации и ошибки обнаружения мошенничества. Эти риски напрямую влияют на конфиденциальность данных и способность системы выявлять подозрительные операции, поэтому их необходимо учитывать при разработке, тестировании и эксплуатации приложения.
